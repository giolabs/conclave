# /conclave-spike

A **spike** is research with a deadline: it buys knowledge, not features. Use it when a story cannot be estimated, an epic's design depends on something nobody has measured, or two options look equally good on paper.

```
/conclave-spike "Can Postgres LISTEN/NOTIFY carry our realtime load or do we need Redis?" --epic EP-003
/conclave-spike "<question>" --timebox S
/conclave-spike                                   # asks for the question
```

The command writes one story with `type: spike` — a single question, a timebox (`XS | S | M`), declared outputs and 2–3 Gherkin scenarios that check the **deliverable**, not production behaviour. Nothing is committed. Added in v2.1.0.

## Where spikes come from

| Source | How |
|---|---|
| Inception | The Tech Lead risk pass marks an epic `uncertainty: high` and lists its open questions; the roadmap schedules `spike:EP-NNN` one slot ahead. [`/conclave-planning`](/en/commands/planning) turns it into a spike story. |
| Planning | Wave 2 feasibility flags `SPIKE_NEEDED` for a story that cannot be estimated. |
| A SPEC | [`/conclave-spec`](/en/commands/spec) lists an open question with `Resolve by: spike`. |
| Anytime | This command. |

## How a spike flows

```
/conclave-spike      → story type: spike (backlog or active sprint)
/conclave-dev <ID>   → Tech Lead runs it: findings + proposed ADR / draft SPEC, docs-only PR
/conclave-qa <ID>    → checks the deliverable answers the question
/conclave-close      → velocity counts the timebox; findings update the epic
```

A spike reuses the normal [story state machine](/en/state-machine#spikes-reuse-this-exact-state-machine-v210): `backlog → ready → in-progress → review → [verified] → done`. `done` means the knowledge exists, not that a feature shipped.

## What it does

### Step 1 — Workspace

Requires a v2 workspace (`conclave_version >= 2.0.0`) and a clean working tree. Reads `story_prefix`, `project_language`, `delivery.spike_max_timebox` (default `M`) and the Tech Lead model, and finds the active (or draft) sprint, if any.

### Step 2 — Seed

Asks only what the arguments did not give:

1. **Question** — required. "Investigate X" is accepted; the Tech Lead rephrases it as a decision and the checkpoint shows the rewrite.
2. **Epic** — any non-retired, non-done `EP-NNN`, or none.
3. **Timebox** — `XS | S | M`, never above `delivery.spike_max_timebox`. A larger request is refused: *"Split the question — a spike longer than M is a project, not a spike."* Default `S`.
4. **Outputs** — multi-select: `adr` (a decision record), `spec` (draft or revise the epic's SPEC — only offered with an epic), `estimate` (re-size the epic or named stories). `findings` is always included.
5. **Where it lands** — **Backlog** (default) or **Active sprint** (warns that it adds units to a locked sprint).

### Step 3 — Snapshot

Copies the epic, `architecture.md`, the ADR index and the epic's SPEC (if any) to `conclave/context/<timestamp>/`.

### Step 4 — Tech Lead authors the spike

One Tech Lead subagent writes the story (`type: spike`, `question`, `timebox` = `estimate`, `spike_outputs`, `discipline`, priority) and its acceptance file:

- **One question**, phrased as a decision ("Can we …", "Should we …", "Which of A or B …"). Two questions → two spikes.
- Story form: **To decide** · **We will investigate** · **Within** — then stop and report, answered or not.
- Scenarios check the deliverable — e.g. *Given the timebox has ended, When the findings report is read, Then it states a recommendation backed by at least one Tier A or B evidence row*.

If an accepted ADR, the architecture or the SPEC already answers the question, the TL returns `SPIKE_NOT_NEEDED: <reason>` and nothing is written.

### Step 5 — Checkpoint

Shows the rephrased question, timebox, outputs, discipline and scenario names: **Write it** / **Change something** (one re-run) / **Cancel**.

### Step 6 — Write

- **Backlog** → `product/stories-backlog/<PREFIX>-NNN-<slug>.md` + `acceptance/AC-<PREFIX>-NNN.md`, `status: backlog`.
- **Active sprint** → the sprint's `stories/` and `acceptance/`, `status: ready`, assigned to the roster Tech Lead; a row in the sprint's `spec.md` and the timebox units added to `meta.md` `committed_units`.
- The epic gets the ID in `spikes:` and `stories:`; a matching line under `## Open questions (spike candidates)` is suffixed `→ <ID>`.
- A backlog row is appended (title prefixed `Spike:`).

## Spike frontmatter

```yaml
type: spike
question: "Can Postgres LISTEN/NOTIFY carry our realtime load or do we need Redis?"
timebox: "S"                # XS | S | M — equals estimate
estimate: "S"
spike_outputs: [findings, adr]   # findings always; + adr | spec | estimate
findings_path: ""           # set by /conclave-dev once the spike has run
epic: "EP-003"
```

## Running the spike

[`/conclave-dev`](/en/commands/dev) routes every `type: spike` story to the **Tech Lead**, whatever its `discipline`. The TL picks the cheapest evidence that can change the decision (versioned docs, measuring existing code, or a throwaway prototype in a disposable worktree or `lab/<ID>-*` branch), stops at the timebox, and writes:

- `conclave/sprints/SPRINT-NNN/spikes/<ID>-findings.md` from `spike-findings.template.md` — question, approach, evidence table with tiers, options, one recommendation, impact on the backlog (estimate changes, new candidate stories, uncertainty after), follow-ups, and `outcome: answered | partially-answered | not-answered`.
- Each declared output: a `proposed` ADR under `product/adr/`, a `draft` SPEC under `product/specs/`, or new estimates in the findings.

The PR is **docs-only** — markdown under `conclave/`; prototype code never lands in it. `outcome: not-answered` is a legitimate result when the report says honestly what was tried and what to do next.

[`/conclave-qa`](/en/commands/qa) checks the scenarios against the findings and outputs (no UAT, no CI wait), and [`/conclave-close`](/en/commands/close) writes the findings back into the epic: `uncertainty`, `adrs`, `spec`, the answered open question, and new candidate stories.

## Output

```
✓ US-014  Spike: Can Postgres LISTEN/NOTIFY carry our realtime load?
  Timebox: S   Outputs: findings, adr   Epic: EP-003
  Landed in: backlog
```

```bash
git add conclave/ && git commit -m "conclave: spike US-014 — realtime transport"
/conclave-dev US-014       # once it is in a sprint
```

## Guardrails

- Never commits, pushes, or opens a PR.
- A spike has exactly one question and a timebox ≤ `delivery.spike_max_timebox`. Never without a timebox.
- Never writes an ADR or SPEC here — the spike produces them when it runs.
- Writes only under `conclave/product/` (stories-backlog, backlog, the epic's `spikes:` / open questions) and, when landing in the active sprint, that sprint's stories, acceptance, `spec.md` table and `committed_units`.
