# /conclave-planning

Plan **one** sprint: the lowest roadmap slot that is not yet planned.

```
/conclave-planning
```

Run it at the start of every sprint — after `/conclave-init` the first time, after `/conclave-close` every time after. It is one of the three **structural** gates (with QA Verification and Sprint Review) — required in every profile.

```
/conclave-init (once) → /conclave-planning → build (/conclave-dev, /conclave-qa, /conclave-pr-review) → /conclave-close → /conclave-planning → …
```

> **v2.0.0 removed `--all`.** Stories are refined one slot at a time so each sprint's stories reflect what the previous review learned. The multi-sprint view lives in `product/roadmap.md`.

## Three waves

| Wave | Role | Job |
|---|---|---|
| 0 | — (orchestrator) | **Readiness gate** (v2.0.0+): SPEC approved for `needs_spec` epics, spike done or scheduled for `uncertainty: high` epics |
| 1 | Product Manager (+ Tech Lead for enabler and spike entries) | **Refine**: turn the slot's epic(s) into stories with acceptance criteria (from the SPEC's §11 when present); turn `spike:EP-NNN` entries into spike stories; propose the Sprint Goal |
| 2 | Tech Lead | **Feasibility**: check against architecture/ADRs, assign `discipline`, flag under-estimates and cross-story dependencies |
| 3 | Scrum Master | **Plan**: capacity from velocity, assignments, retro action items, planning record |

There is no separate grooming ceremony: refinement happens inline, here, for the epics of the slot being planned.

## What it does

### Gate and slot resolution

- Any sprint still `active` → refuses: run `/conclave-close` first.
- A `draft` sprint left by an interrupted run → resumes it, skipping stories already on disk.
- The **slot** is the lowest row in `product/roadmap.md` with status `planned`. None left → add epics with `/conclave-epic new` or edit the roadmap.
- The sprint ID is the next monotonic `SPRINT-NNN`. With no sprint yet, it is `SPRINT-000` when `sprint.sprint_zero: true`, otherwise `SPRINT-001`.
- A workspace without `product/roadmap.md` (pre-v2) is refused: run `/conclave-init --upgrade`.
- The slot's `Epics` cell may also hold **spike entries** `spike:EP-NNN` (v2.0.0+) — each names an epic whose open questions this sprint answers; the epic itself may sit in a later slot.

### Readiness gate — SPECs and spikes (v2.0.0+)

Before refining, each epic of the slot is checked. An epic without `uncertainty` / `needs_spec` (written by hand) is treated as `low` / `false` and skips the gate.

- **SPEC** — `needs_spec: true` and no `approved` SPEC:
  - `delivery.spec_gate: require` → refuses: run [`/conclave-spec EP-NNN`](/en/commands/spec) and `/conclave-spec approve SPEC-NNN` first (or set `needs_spec: false`).
  - `delivery.spec_gate: warn` (default) → asks: **Write the SPEC now** (runs `/conclave-spec` inline, then offers to approve it) · **Plan without it** (refines from candidate stories; the risk is recorded in `planning.md`) · **Spike first** (the epic moves to the next planning and a `spike:EP-NNN` entry is added if open questions remain).
- **Uncertainty** — `uncertainty: high`, no `done` spike and no spike entry in this slot → asks: **Spike in this sprint, feature stories after** · **Spike and stories together** (the PM refines only stories that do not depend on the open question) · **Accept the risk**.

Every decision is written into `planning.md` under commitments and risks.

### Inputs

Vision (Product Goal), roadmap, the slot's epics, architecture and ADRs, DoR, backlog, roster, plus:

- **Carry-over** — stories the last review marked "next sprint".
- **Backlog pull candidates** — `backlog` stories whose `epic` is in the slot.
- **Retro actions** — open action items from the previous `retro.md` (when `ceremonies.close.retro: true`).
- **Velocity history** — `velocity` from the last 3 `closed` sprints.
- **SPECs** — for each slot epic with a `spec`, its §3 decisions, §7 domain rules, §9 test strategy and §11 story breakdown.
- **Spike findings** — of each slot epic's `done` spikes (re-estimates, new candidate stories).
- **Domain rules** — when `product_doc_path` points to a [`/conclave-discovery`](/en/commands/discovery) package, its `03-bloc.md` (invariants, use cases, edge cases).

### Questions

Always: sprint start date (default today), end date (default start + `sprint.length_weeks`), facilitator. `full-scrum` also asks about PTO or partial availability.

### Wave 1 — refinement

The Product Manager proposes a **Sprint Goal** traceable to the slot goal and writes one story + acceptance pair per new story: `type: feature`, `epic: EP-NNN`, priority, estimate, dependencies, 2–4 Gherkin scenarios. No `XL` — it splits first. Existing backlog candidates are reused, not duplicated.

**From a SPEC** (v2.0.0+). When the epic has a SPEC, its §11 Story breakdown **replaces** the candidate stories as the source: one story per row, same order and dependencies, each with `spec: SPEC-NNN` and the `adrs:` its row implements. The PM does not redesign — a row it disagrees with is flagged as a `Spec concern` and refined as written.

**BLOC → Gherkin.** When the discovery package's `03-bloc.md` is present, the PM gets it too: every invariant, use case or edge case a story touches must appear as a Gherkin scenario on that story. This is the one part of the product package read at every planning, not just at inception.

When the slot contains a `type: enabler` epic, the Tech Lead writes `type: enabler` stories ("In order to / We need") whose acceptance criteria a script can check. For Sprint 0 the minimum set is: scaffold for the confirmed stack, test framework + one passing test, lint, a CI workflow running both on PRs, and the `develop` integration branch.

**Spike stories** (v2.0.0+). For each `spike:EP-NNN` entry, the Tech Lead turns the epic's open questions (and SPEC §12 rows marked `Resolve by: spike`) into `type: spike` stories — one question each, timebox ≤ `delivery.spike_max_timebox`, declared outputs, 2–3 scenarios that check the deliverable. Questions that already have a spike are skipped. Spike stories go into the epic's `spikes:` list too. See [`/conclave-spike`](/en/commands/spike).

### Wave 2 — feasibility

The Tech Lead validates every story in the draft against the architecture, ADRs and the epic's SPEC, names cross-story dependencies (a feature story that depends on a spike in the same sprint lists it), flags under-estimates, and **assigns a `discipline`** (`frontend | backend | qa | design | devops | mobile | multi`).

A story that cannot be estimated because of an unknown gets `SPIKE_NEEDED: <story> — <question>`, and you choose per finding: **add a spike and move the story to the backlog**, **add a spike and keep the story** (it depends on the spike), or **keep the story as is** (risk recorded).

### Wave 3 — planning record

The Scrum Master assigns each story to a roster member whose discipline matches, carries in retro actions, and writes the planning record.

### Validation

- **DoR** — a failing story can be dropped back to `backlog` or fixed now (re-runs the PM for that story). In `full-scrum` the sprint cannot lock while a failing story stays selected.
- **Capacity** — units `XS=1, S=2, M=3, L=5, XL=8`; a spike counts its `timebox`. Capacity is the **average velocity of the last 3 closed sprints**. With no closed sprint yet it falls back to `num_devs × length_weeks × 5` (minus PTO) and is labelled *"fixed formula — no velocity yet"*. A closed Sprint 0 counts as history only if it delivered at least one unit.
  - Over `1.2 × capacity` → drop the lowest-priority story or keep it and record the risk.
  - Under `0.6 × capacity` with more candidates in the slot → offer to pull the next one.
- **Coverage gaps** — no roster member for a story's discipline → asks whether to assign the Tech Lead as a fallback.

### Lock

`meta.md` → `status: active` with dates and `committed_units`; `spec.md` and `planning.md` written; stories → `status: ready` with assignee and discipline; backlog rows updated (Epic column filled); the slot's epics `proposed` → `active`; the roadmap slot → `active` with the sprint ID and real dates.

## Output

```
✓ SPRINT-001 is active (2026-10-12 → 2026-10-23) — slot 1: <slot goal>
  Sprint Goal: <one sentence>
  Epics:       EP-001, EP-002

  US-001 → Bea (frontend) [M]  EP-001
  US-002 → Fen (devops)   [S]  EP-000 enabler
  US-003 → Ada (backend)  [S]  EP-004 spike: <question>

  Capacity: 14 / 15 units — velocity avg of SPRINT-000..000
  SPECs:    EP-002 ← SPEC-001 (approved) · EP-003 planned without SPEC (risk)
  Retro actions carried in: 1
```

## Guardrails

- Writes only inside `conclave/`. Never commits.
- `sprint_planning` and `qa_verification` are structural — a config setting either to `required: false` is refused.
- Exactly one sprint may be `active`: never plans while one is active.
- Never generates stories for epics outside the slot. Spike entries are the one exception — `spike:EP-NNN` refines only the epic's open questions, never its feature stories.
- Never writes or approves a SPEC or ADR except through the inline `/conclave-spec` path of the readiness gate, which keeps that command's checkpoint.
- Preserves hand-edits in story files, `spec.md` and `planning.md` when resuming a draft.

## After it runs

```bash
git add conclave/ && git commit -m "conclave: plan SPRINT-NNN — <sprint goal>"

/conclave-dev US-001        # one story
/conclave-dev --loop        # autonomous three-wave loop over the sprint
/conclave-close             # at sprint end
```
