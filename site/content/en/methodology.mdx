# Methodology

Conclave assumes standard **Scrum** with practical accommodations real engineering teams make: a **discipline-first roster** (every project has Tech Lead, Frontend, Backend, QA, Designer, and DevOps work, whether or not it has a dedicated Product Manager or Scrum Master), and **git** as the team's coordination substrate.

## The Scrum mapping

| Scrum concept | Conclave term | Notes |
|---|---|---|
| Development Team | **Disciplines: Tech Lead, Frontend, Backend, QA, Designer, DevOps** | Always present in the roster, even on a solo project where one person covers all six. This is the primary roster axis. |
| Product Owner | **Product Manager (PM)** | An optional process role any discipline-holder can additionally carry — owns the backlog, prioritizes, defines acceptance, when someone holds it. Most teams call it PM in practice. |
| Scrum Master | **Scrum Master (SM)** | An optional process role. Facilitates ceremonies, surfaces blockers, when someone holds it. If nobody does, the Tech Lead and team decide process by consensus. |
| Product Goal | `conclave/product/vision.md` | One measurable outcome the MVP commits to, written at inception. |
| Epic | `conclave/product/epics/EP-NNN-<slug>.md` | A big chunk of value with a success criterion. Not a Scrum Guide term, but the layer between the Product Goal and stories. |
| Product Backlog | `conclave/product/backlog.md` + epics' candidate stories | Ordered list of refined stories; rough candidates live in their epic until planning refines them. |
| Roadmap / release plan | `conclave/product/roadmap.md` | How many sprints (`horizon`: auto or a fixed N), epics and spike entries sequenced into sprint slots, epics beyond the horizon, burnup and forecast. Re-forecast at every close; re-sequenced by `/conclave-roadmap replan`. |
| Spike | Story with `type: spike` | Timeboxed (XS–M) research answering one question. Produces a findings report and, when declared, a proposed ADR or draft SPEC. Run by the Tech Lead. (v2.0.0+) |
| Architecture decision | `conclave/product/adr/ADR-NNN-<slug>.md` | One decision with alternatives and evidence. `proposed → accepted \| superseded`. |
| Technical specification | `conclave/product/specs/SPEC-NNN-<slug>.md` | The design of one epic composed from its ADRs: contracts, data, tests, rollout, story breakdown. `draft → approved \| superseded`. (v2.0.0+) |
| Sprint Backlog | `conclave/sprints/SPRINT-NNN/spec.md` selected stories table | Snapshot at planning time. |
| Increment | Stories `done` in the sprint (QA-verified, TL-approved when on) | Conclave never merges; whether a human merged each PR is reported at close. |
| Sprint Planning | `/conclave-planning` | Plans one roadmap slot, refining its epics just in time. Structural gate. |
| Backlog refinement | Inside `/conclave-planning` | No separate grooming ceremony. |
| Daily Scrum | The [board](/en/commands/board) + story statuses | No standup command. |
| Sprint Review | `/conclave-close` | Inspects the Increment against the Sprint Goal, records velocity, re-plans the roadmap. Structural gate. |
| Sprint Retrospective | `/conclave-close` | Runs when `ceremonies.close.retro: true`; at most 3 action items, imported by the next planning. |
| Definition of Ready | `conclave/product/definition-of-ready.md` | Team-customized checklist a story must pass before entering a sprint. |
| Definition of Done | `conclave/product/definition-of-done.md` | Team-customized checklist a story must meet to reach `done`. |
| User story | One file under `sprints/SPRINT-NNN/stories/` | INVEST format. |
| Acceptance criteria | One file under `sprints/SPRINT-NNN/acceptance/` | Gherkin Given/When/Then. |

## Knowledge before code (v2.0.0+)

An epic says **what** and **why**. Before its stories are refined, the team may need to learn something, decide something, or design something. Conclave makes that path explicit:

```
Epic (what · why)  →  Spike(s) (unknowns, timeboxed)  →  ADR(s) (one decision each)  →  SPEC (how: the epic's design)  →  Stories (/conclave-planning)
```

| Step | Artifact | Command |
|---|---|---|
| Epic | `product/epics/EP-NNN-*.md` with the Tech Lead's risk assessment: `uncertainty`, `needs_spec`, open questions | `/conclave-init`, [`/conclave-epic`](/en/commands/epic) |
| Spike | A `type: spike` story with one question and a timebox; ships a findings report, not code | [`/conclave-spike`](/en/commands/spike), or a `spike:EP-NNN` roadmap entry refined at planning |
| ADR | One decision, its alternatives and evidence | [`/conclave-adr`](/en/commands/adr), or produced by a spike / a SPEC |
| SPEC | The epic's design composed from its ADRs, ending in a story breakdown | [`/conclave-spec`](/en/commands/spec) |
| Stories | Refined just in time from the SPEC's §11 (or the epic's candidate stories) | [`/conclave-planning`](/en/commands/planning) |

Every step is optional for a well-understood epic and enforced only where the epic says so:

- `uncertainty: high` → the roadmap schedules `spike:EP-NNN` one slot ahead, and planning offers the spike before the feature stories.
- `needs_spec: true` → planning requires (or warns about, per `delivery.spec_gate`) an approved SPEC, and refines the stories from its breakdown.

A spike is a real story — planned, sized by its timebox, counted in velocity, verified by QA on its deliverable — but it ships knowledge, not code.

## Release planning — how many sprints

The roadmap is the release plan. Its **horizon** (`sprint.planned_sprints`) is either `auto` — as many sprints as the `must` and `should` epics need — or a fixed number chosen at `/conclave-init` or with [`/conclave-roadmap replan --sprints N`](/en/commands/roadmap). With a fixed number, epics that do not fit are listed under *Beyond the horizon* in priority order, never silently dropped, and the forecast says if a `must` epic is among them. Capacity per slot comes from real velocity once a sprint has closed.

Solo developers get their own setup path: `/conclave-init` asks up front whether the project is solo or a team. Solo mode forces the `lean` profile and renders a single-person roster covering every discipline; team mode asks who covers each of the six disciplines (name + GitHub handle, or `TBD`) plus who — if anyone — holds the PM/SM process roles.

## The artifact tree

At the root of the team's repo, Conclave maintains a visible `conclave/` directory. Everything is markdown.

```
conclave/
├── README.md                         # explains the directory on GitHub
├── config.md                         # project type, stack, team_mode, team_profile
├── team/
│   ├── roster.md                     # who covers which discipline, plus optional PM/SM
│   └── ceremonies.md                 # cadence
├── product/                          # persists across sprints
│   ├── vision.md                     # Product Goal
│   ├── roadmap.md                    # slots, burnup, forecast
│   ├── epics/EP-NNN-<slug>.md
│   ├── backlog.md
│   ├── architecture.md
│   ├── adr/ADR-NNN-<slug>.md         # official ADRs
│   ├── specs/SPEC-NNN-<slug>.md      # technical spec per epic (v2.0.0+)
│   ├── definition-of-ready.md
│   └── definition-of-done.md
├── context/                          # frozen snapshots of inputs
└── sprints/
    └── SPRINT-NNN/
        ├── meta.md                   # status, slot, epics, committed units, velocity
        ├── spec.md                   # sprint plan
        ├── planning.md               # planning record
        ├── review.md                 # /conclave-close
        ├── retro.md                  # /conclave-close, when retro is on
        ├── stories/
        │   └── US-NNN-<slug>.md
        ├── acceptance/
        │   └── AC-US-NNN.md
        └── spikes/                   # <PREFIX>-NNN-findings.md, one per spike run (v2.0.0+)
```

## Invariants every Conclave command respects

- **Markdown only.** Structured fields live in YAML frontmatter. The body is human-readable prose.
- **Visible directory.** `conclave/` is not hidden — it renders on GitHub and is discoverable.
- **Append, do not clobber.** Each `/conclave-planning` run creates the next `SPRINT-NNN/` and updates `product/backlog.md` additively; it never overwrites previous work. `/conclave-init --upgrade` migrates frontmatter in place but never deletes or renames a sprint, story, or report.
- **Snapshot context.** Every artifact-generating command writes a fresh snapshot under `conclave/context/` so the artifact is auditable against the inputs that produced it.
- **Reference, do not duplicate.** Stories reference their acceptance file; sprint spec references `product/definition-of-done.md` rather than copying it.
- **Numbering is sticky.** `SPRINT-NNN`, `EP-NNN`, `US-NNN`, `ADR-NNN` and `SPEC-NNN` IDs increment monotonically and are never reused.
- **Agents propose, humans approve.** ADRs are always written `proposed` and SPECs `draft`; only a human accepts an ADR or approves a SPEC (`/conclave-spec approve`).
- **Spikes ship docs, not code.** A spike's PR holds only markdown under `conclave/`; prototypes stay on a lab branch or worktree.
- **One active sprint.** `/conclave-planning` refuses while a sprint is `active`; only `/conclave-close` sets it `closed`.
- **Roster schema degrades gracefully.** A `roster.md` written before the discipline model shipped (no `Discipline` column) is not rejected — commands treat every member as `multi`-discipline and print a one-time compatibility hint.

## How slash commands invoke role subagents

Each slash command is a markdown orchestrator. Its body says, in prose: *"Spawn a subagent loaded with `skills/conclave/agents/<role>.md` to produce X."*

Claude reads the role charter file, dispatches an `Agent` tool call with that content as the system-prompt prefix, and continues when the subagent returns. Independent roles run in parallel by issuing both `Agent` calls in a single message (PM + TL in `/conclave-init` inception, before the SM writes the roadmap). `/conclave-planning` runs in three waves: PM refinement, then TL feasibility and discipline assignment, then SM planning — assignment needs to know each story's discipline before it can pick a valid assignee.

There is no DSL. The pattern is the same one Anthropic's own `code-review` plugin uses for its parallel review agents.

## How teams coordinate

Each team member runs their own local Claude Code. The shared state lives in `conclave/` and is committed to git. Coordination happens through pull requests:

- PM adjusts epics (`/conclave-epic`) or stories (`/conclave-story`) → opens a PR to `conclave/product/`.
- Dev, Designer, or DevOps picks up a story (whichever matches its `discipline`) → branches `feat/US-NNN-<slug>` → implements → opens a PR.
- QA verifies → appends a verification report to the acceptance file → PR comment.
- TL approves the code (when `peer_pr_review.required: true`) → runs `gh pr review --approve`.
- At sprint end, the facilitator runs `/conclave-close` → opens a PR with the review, retro, velocity and roadmap update.

There is no central server, no proprietary state, no surface for vendor lock-in. The team owns the workflow because the workflow is just files in their own repo.
