# /conclave-qa US-NNN [US-NNN ...] [--lab]

Verifica una o más historias de usuario en `status: review` contra sus criterios de aceptación — o, con `--lab`, ejecuta un lab test post-merge.

```
/conclave-qa US-001                   # historia única — comportamiento idéntico al anterior
/conclave-qa US-001 US-002 US-003     # tres historias en paralelo, en la rama de integración
/conclave-qa US-001 --lab             # ejecuta el lab test de US-001 (post-merge, una sola historia)
/conclave-qa BUG-004 --lab            # ejecuta el lab test de BUG-004
```

`--lab` solo se acepta para un único ID de historia o bug, y solo después de que el PR ya fue mergeado. No corre verificación Gherkin — corre la spec del lab del Tech Lead en su lugar.

Cuando termina, cada historia pasó a uno de cuatro estados:

- **`verified`** — QA pasó, esperando la aprobación de PR del Tech Lead. Pasa cuando `peer_pr_review.required: true`.
- **`done`** — QA pasó y no hay un gate separado del TL. Pasa cuando `peer_pr_review.required: false`.
- **`review` (UAT pendiente)** — se generaron y pushearon artefactos de UAT y nada falló, pero un checklist de mobile está esperando a una persona, o quedó incompleto. No es un defecto.
- **`review` (con bloqueos)** — QA encontró fallas — en los escenarios Gherkin, la DoD, o la corrida de CI de los tests UAT generados. El dev (o la persona tester) arregla, y QA vuelve a correr.

Este es uno de los dos gates **estructurales** de Scrum que Conclave hace cumplir (junto a Sprint Planning). No se puede saltar en ningún perfil. **QA no aprueba el PR él mismo** — la aprobación a nivel de código le corresponde al Tech Lead vía `/conclave-pr-review`. El veredicto de QA va al reporte de verificación y a un comentario en el PR.

## Comportamiento multi-historia

Cuando se pasa más de un ID de historia, aplica el mismo patrón de validación anticipada → batches concurrentes de ≤ 3 → aislamiento de fallos → tabla de resumen final que en `/conclave-dev`. Cada subagente de QA corre completamente independiente en la rama de integración, incluyendo generación de UAT, espera al CI, y comentario en el PR. Una tabla de resumen final muestra el veredicto de cada historia:

```
| Historia | PR                           | Veredicto           |
|----------|------------------------------|---------------------|
| US-001   | https://github.com/…/pull/42 | ✓ passed            |
| US-002   | https://github.com/…/pull/43 | ✗ blocked (2 ítems) |
| US-003   | https://github.com/…/pull/44 | ⏳ pending_uat       |
```

## Qué hace

1. Resuelve el workspace y confirma `qa_verification.required: true` (siempre true — se rehúsa si una config mal formada dice lo contrario).
2. Resuelve la historia — debe estar en `status: review`. Lee `repo.integration_branch` de `config.md` (default `develop`).
3. **Cambia a la rama de integración** (`develop` o el `repo.integration_branch` configurado). Captura la URL del PR de la feature branch de esta historia (`feat/US-NNN-<slug>`) vía `gh pr list` — la feature branch no necesita estar chequeada. La verificación se ancla al estado integrado del codebase, no a la feature branch aislada.
4. Carga contexto en paralelo: config, DoD, historia, archivo de aceptación, `conclave/team/testing-environments.md`, las plantillas de verification-report/UAT-report, y metadata del PR (reviews, status de CI) si `gh` está disponible. Si `testing-environments.md` falta o cada fila sigue en `TBD`, UAT se salta para esta corrida — QA verifica exactamente como siempre lo hizo.
5. **Genera artefactos de test UAT**, cuando UAT está habilitado, según la `discipline` de la historia:
   - `frontend` / `multi` → un spec de Playwright (`tests/uat/US-NNN.spec.ts`), un caso de test por escenario Gherkin.
   - `backend` / `multi` → mergea los endpoints de esta historia en la única colección, compartida y en evolución, `tests/uat/api-collection.postman_collection.json`, corrida vía Newman — nunca sobreescribe los requests de otra historia.
   - `mobile` → un checklist funcional manual (`tests/uat/US-NNN-UAT.md`) para que una persona tester lo ejecute y registre un veredicto. Sin espera de CI para mobile.
   - Si todavía no hay ningún job de CI que corra `tests/uat/`, propone la adición mínima y confirma con el humano vía `AskUserQuestion` antes de escribirla.
6. **Pushea y espera al CI** (se salta para `mobile`) — sondea la corrida de CI disparada por el commit pusheado, hasta `ceremonies.qa_verification.ci_wait_timeout_minutes` (default 20). Una falla de CI, o ninguna corrida encontrada / una espera que expira, se trata exactamente igual que un escenario Gherkin que falla.
7. **Delega al subagente de QA**, que re-deriva PASS/FAIL para cada escenario Gherkin desde cero — de forma adversarial, no confiando en lo que dice el propio dev — e incorpora el resultado de UAT/CI (o el estado actual de un checklist de mobile en una corrida posterior).
8. Escribe las salidas (abajo):
   - **8.1 — Passed**: salidas de verificación estándar (abajo).
   - **8.2 — Blocked**: además de la sección `## QA blockers` estándar, cada defecto reproducible vinculado a una historia específica se escribe como un archivo de bug del sprint:
     - Ruta: `conclave/sprints/<SPRINT_ID>/bugs/BUG-NNN-<slug>.md`
     - El frontmatter incluye: `linked_story`, `linked_acceptance` (ruta del archivo), `introduced_by_pr` (URL del PR de la feature), `severity` (`minor | major | critical`), `status: open`.
     - Un sprint **no puede cerrarse** si algún archivo en `conclave/sprints/<SPRINT_ID>/bugs/` tiene `severity: critical` y `status` distinto de `done`.

QA nunca ejecuta los tests generados él mismo — lo hace el propio CI del repo target, y nunca resuelve, lee, ni escribe un valor de secreto en ningún momento.

### Historias spike (v2.0.0+)

Una historia `type: spike` entrega conocimiento, no comportamiento, así que UAT y la espera de CI (pasos 5–6) se saltean. QA lee el reporte de hallazgos (`findings_path`), cada ADR que produjo el spike y su SPEC, y verifica cada escenario Gherkin contra ellos:

- Los hallazgos existen, repiten la pregunta, y el `outcome` es honesto — una recomendación apoyada solo en evidencia Tier D cuenta como `not-answered`.
- Existe cada salida de `spike_outputs`: un ADR con `status: proposed` y sección Decision, una SPEC con `status: draft`, re-estimaciones listadas en "Impact on the backlog".
- El diff del PR tiene solo markdown bajo `conclave/` — cualquier código de aplicación o de prototipo es un veredicto `blocked`.
- `outcome: not-answered` **no** es una falla en sí: pasa si el reporte dice qué se probó, por qué no convergió y qué hacer después.

Los veredictos son `passed` / `blocked`; nunca `pending_uat`.

## Qué produce

- Una sección `## Verification — <fecha>` **agregada** a `acceptance/AC-US-NNN.md` — nunca sobreescribe corridas de verificación previas, ahora incluyendo una subsección de ejecución de UAT (corrida de CI + resultado, o el estado del checklist de mobile).
- Nuevos artefactos de UAT commiteados al repo target bajo `tests/uat/` (cuando UAT está habilitado).
- Actualización del frontmatter de la historia:
  - Veredicto `passed` + `peer_pr_review.required: true` → `status: verified`.
  - Veredicto `passed` + `peer_pr_review.required: false` → `status: done` directamente.
  - Veredicto `pending_uat` → se queda en `status: review`, con una sección `## QA pending` nombrando qué necesita completar una persona — redactado como esperando finalización, no como un defecto.
  - Veredicto `blocked` → se queda en `status: review`, con una sección `## QA blockers` listando cada escenario/ítem de DoD/falla de CI y su reproducción o evidencia (extracto de log + URL de la corrida de CI).
- `conclave/sprints/<SPRINT_ID>/bugs/BUG-NNN-<slug>.md` — un archivo por defecto reproducible encontrado (solo en veredicto blocked).
- Un **comentario** en el PR con el veredicto (nunca una review/aprobación — `gh pr review` nunca se llama desde acá).

## Archivos de bugs del sprint

Cuando QA queda bloqueado, cada defecto reproducible se convierte en un archivo de bug del sprint en:

```
conclave/sprints/SPRINT-NNN/bugs/BUG-NNN-<slug>.md
```

El archivo vincula de vuelta a la historia, sus criterios de aceptación, y el PR que introdujo la regresión. Los bugs con `severity: critical` bloquean el cierre del sprint. Estos archivos son **distintos** de los bugs reportados manualmente vía `/conclave-bug report` (que van a `conclave/product/bugs/`).

## Ejecución de lab test (`--lab`)

Cuando se pasa `--lab`, los pasos de verificación Gherkin estándar se reemplazan por la ejecución del lab test. Esto requiere:

- `lab_test.enabled: true` en `conclave/config.md`
- Un archivo de spec del lab (`US-NNN-lab.md` o `BUG-NNN-lab.md`) ya escrito por el Tech Lead
- `conclave/lab-config.md` presente y en .gitignore (hard stop si falta)
- El PR de esta entidad ya mergeado en `lab_test.integration_branch`

### Qué hace `--lab`

1. Carga `conclave/lab-config.md`, lee el variable registry, confirma que el archivo está en .gitignore.
2. Cambia a `LAB_TEST_BRANCH`, captura el SHA del commit (`LAB_SHA`).
3. Selecciona las vars del entorno `integration` (con confirmación del usuario si `integration.vars` está vacío, fallback a `local.vars`).
4. Exporta las vars de entorno de integración al shell (los valores nunca se imprimen). Genera `LAB_TEST_TAG=lab-<timestamp>`.
5. **Pre-checks de seguridad** (hard abort si cualquiera falla):
   - `payment_mode` debe ser igual a `test`
   - `STRIPE_SECRET_KEY` debe empezar con `sk_test_`
6. Ejecuta el comando Verify de la spec del lab, con el timebox configurado. Captura el exit code y 200 chars de output.
7. Agrega una fila al Evidence log en la spec del lab (Tier A: comando + exit code + output + SHA). Actualiza `status`, `last_run_at`, `last_run_sha`.
8. **Si falló**: despacha el subagente QA para escribir un reporte de bug. El bug se escribe en `conclave/product/bugs/BUG-NNN-lab-failure-<slug>.md`. Se actualiza `linked_bug` en la spec del lab.
9. Commitea y pushea la spec del lab (con el Evidence log actualizado) a `LAB_TEST_BRANCH`.

Un timeout durante la ejecución resulta en `status: blocked` (no `failed`). Las specs bloqueadas pueden re-correrse después de resolver el timeout.

Ver [Lab tests](/es/lab-tests) para la referencia completa incluyendo reglas de seguridad, patrones de idempotencia, y apertura de bugs.

## Salvaguardas

- Solo modifica `conclave/`, el archivo de aceptación de esta historia, y `tests/uat/US-NNN.spec.ts` / los archivos compartidos de colección+environment de Postman / `tests/uat/US-NNN-UAT.md` — QA escribe reportes de verificación y artefactos de UAT, QA no arregla código.
- Puede proponer (con confirmación humana) agregar el único job/step de CI que corre `tests/uat/` — ningún otro cambio de pipeline.
- Nunca borra secciones de verificación previas — el archivo de aceptación es el registro de auditoría completo de la historia.
- Nunca sobreescribe los requests de otra historia en la colección compartida de Postman.
- Nunca resuelve, lee, ni escribe un valor de secreto, en ningún lado, en ningún paso — incluyendo durante la ejecución de `--lab` (los valores se exportan al shell; QA nunca los ve).
- Nunca corre `gh pr review --approve` ni `--request-changes`. Esa es decisión del Tech Lead vía `/conclave-pr-review`.
- Nunca pasa una historia cuando algún escenario falla, algún ítem requerido de DoD no se cumple, o la corrida de CI de los tests UAT generados falló o expiró.
- Nunca confunde `pending_uat` con `blocked`.
- No mergea el PR, ni siquiera cuando el veredicto produce `status: done` directamente.
- `--lab` es solo para una entidad, post-merge — nunca se acepta en batch ni antes de que el PR mergee.
- `--lab` nunca imprime los valores de las vars — solo los nombres de variables aparecen en los logs.

## Después de que corre

- **Veredicto `passed`, `peer_pr_review.required: true`** — el Tech Lead corre [`/conclave-pr-review US-NNN`](/es/commands/pr-review) para aprobar y mergear.
- **Veredicto `passed`, `peer_pr_review.required: false`** — sin gate separado; el PR está listo para mergear.
- **Veredicto `pending_uat`** — una persona completa `tests/uat/US-NNN-UAT.md` (checklist de mobile), después se vuelve a correr `/conclave-qa US-NNN`.
- **Veredicto `blocked`** — el dev arregla y pushea (o una persona tester de mobile registra un FAIL con notas), después se vuelve a correr `/conclave-qa US-NNN`. Los archivos de bugs del sprint permanecen abiertos hasta que el fix sea verificado.

Después de que el PR mergea (y `lab_test.enabled: true`):
- **Lab test `passed`** — evidencia Tier A en el Evidence log de la spec del lab. Listo.
- **Lab test `failed`** — se escribió un archivo de bug en `conclave/product/bugs/`. Arreglar y re-correr `/conclave-qa US-NNN --lab`.
- **Lab test `blocked`** — el comando Verify expiró o la spec del lab no tenía ningún comando ejecutable. Revisar la spec y re-correr después de resolver el problema.
