# Primeros pasos

Conclave corre en **Claude Code o Cursor** contra el mismo directorio `conclave/`.

- **¿Cursor y nunca instalaste Conclave?** Seguí primero [Cursor desde cero](/es/installation#cursor-desde-cero) (clonar el plugin → instalar → después inicializar **tu app**).
- Si no, instalá tu runtime vía [Instalación](/es/installation) / [Plataformas](/es/platforms), y después:

## Dos comandos para arrancar

Dentro de cualquier repo git:

```bash
# 1. Wizard único — detecta el stack, reúne nombre del proyecto, prefijo de historia,
#    fecha de lanzamiento, perfil de equipo, y ubica el documento de producto. Sin agentes de IA.
/conclave-init

# 2. Generá historias + arquitectura desde el doc de producto y bloqueá el Sprint 1 como activo.
#    Usá --all para planificar todos los sprints del documento en un solo paso.
/conclave-planning
/conclave-planning --all
```

Eso es todo. Después del paso 2 el sprint está `active`, cada historia tiene un asignado y una disciplina, y el equipo puede abrir un PR con todo el directorio `conclave/`.

`/conclave-init` es un **wizard puro** (sin agentes de IA). Auto-detecta tu stack y después pregunta: nombre del proyecto, prefijo de ID de historia (ej. `US`, `TASK`, `FEAT`), idioma del proyecto, fecha de lanzamiento, modo de equipo (solo/equipo) y perfil de equipo. También ubica el documento de planificación del producto — o te ayuda a crearlo.

`/conclave-planning` hace el resto. En la **primera corrida** invoca al Tech Lead y al Product Manager en paralelo — leyendo tu documento de producto — para producir el backlog, la arquitectura, los archivos de historias y los criterios de aceptación en Gherkin. Después (en **cada corrida**) corre la ceremonia de Sprint Planning.

## Qué se crea

Después de correr ambos comandos, tu repo tiene un directorio `conclave/` completo:

```
conclave/
├── README.md
├── config.md                         # story_prefix, product_doc_path, config del equipo
├── team/
│   ├── roster.md                     # quién cubre cada disciplina, más PM/SM opcionales
│   └── ceremonies.md
├── product/
│   ├── backlog.md                    # Product Backlog ordenado (de /conclave-planning)
│   ├── architecture.md               # ADRs + decisiones técnicas (de /conclave-planning)
│   ├── definition-of-ready.md
│   └── definition-of-done.md
├── context/                          # snapshots congelados de los inputs usados
└── sprints/
    └── SPRINT-001/
        ├── meta.md
        ├── spec.md                   # plan del sprint
        ├── planning.md               # acta de la reunión de planning
        ├── stories/                  # un archivo por historia (PREFIJO-001-slug.md)
        └── acceptance/               # criterios de aceptación Gherkin (AC-PREFIJO-001.md)
```

Cada archivo es markdown. Cada cambio es un diff de git normal que tu equipo puede revisar en un PR.

## Continuando el loop

Una vez que el Sprint 1 está bloqueado:

```bash
# Cada dev toma la historia que le asignaron
/conclave-dev US-001

# QA verifica la historia cuando llega a review
/conclave-qa US-001

# Tech Lead aprueba el PR (solo en perfiles donde peer_pr_review está activo)
/conclave-pr-review US-001
```

Cuando todas las historias del sprint están `done`, estás listo para el próximo ciclo de planning. Corré `/conclave-planning` para el `SPRINT-002` — la Fase A se saltea (el backlog ya existe), solo corre la ceremonia de planning.
